## โฮสต์และข้อจำกัด

Cloudflare ใช้ vinext + Workers ที่ตั้งไว้เดิม และ Pages service binding ไป Worker เดียวกัน.
deploy ด้วย `--skip-build --ci` ใช้ secrets เดิมบน Worker ไม่มีการ upload ค่าใหม่.
API limiter เพิ่มเฉพาะ binding; ดึงค่าตั้งค่าหลัง deploy ยืนยัน type=ratelimit และ limit/period ตรงจริง.
Logs/traces เปิดแล้ว และ redact_query_string=true. ยังไม่มีหลักฐานระบบ alert ไปผู้ดูแลภายนอก.
ไม่มี custom domain zone ในบัญชี จึงยังใช้ zone WAF rules กับ pages.dev/workers.dev ไม่ได้.
Worker rate binding เป็น counter ต่อ Cloudflare location แบบ eventual consistency ไม่ใช่ global cost cap.
คง quota AI ฝั่งฐานข้อมูลและเพดาน request ไว้ด้วย.

Vercel plugin GET projects และ CLI project inspect talevo --scope etcstream ตอบ 403 Not authorized.
เว็บเดิมยังตอบ 200/401 และมี headers แต่ยังเผยแพร่ security build ใหม่ขึ้น Vercel ไม่ได้.
ผู้ใช้แจ้งว่าติด deployment limit ด้วย; session นี้ไม่มีสิทธิ์อ่าน quota เพื่อยืนยันชนิด/เวลาหมดลิมิต.
ไม่อัปเกรดแพ็กเกจหรือเพิ่มค่าใช้จ่ายเพื่อข้ามข้อจำกัด.
ตัวส่ง Web Push เดิมยังอยู่บน Vercel จึงต้องตรวจแยกหากลิมิตกระทบ runtime.

## สิ่งที่เจ้าของต้องทำเอง

ชื่อ env สำหรับ host: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`,
`SUPABASE_SECRET_KEY`, `TALEVO_AI_PROVIDER`, `GROQ_API_KEY`, `TALEVO_AI_MODEL`,
`NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `TALEVO_CLOUDFLARE=1`, `TALEVO_PUSH_DELIVERY=external`.
ตัวส่ง Push บน Vercel ใช้ `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `PUSH_DISPATCH_SECRET` เพิ่มเติม.
`GEMINI_API_KEY`, `TALEVO_VISION_MODEL`, `TALEVO_TIMETABLE_MODEL` เป็นค่าทางเลือกตาม provider/ฟีเจอร์;
ถ้าเปลี่ยน provider ต้องตรวจ binding Cloudflare และทดสอบก่อน.
Worker ปัจจุบันมี secrets เดิมครบตาม provider Groq; ครั้งนี้ไม่ได้ตั้ง env ใหม่.

1. ตรวจ `supabase/manual/review_restrict_rls_auto_enable_execution_20261117.sql` ก่อนรันใน SQL Editor:
   revoke EXECUTE ของ internal event trigger จาก PUBLIC/anon/authenticated เท่านั้น ไม่ลบข้อมูล/trigger และไม่ปิด RLS.
   หลังรัน query ตรวจท้ายไฟล์ต้องได้ false ทั้งสอง role. ไม่รัน security-hardening.sql ชุดเก่าซ้ำ เพราะ limiter ติดตั้งแล้ว.
2. ให้บัญชีที่เชื่อม Vercel มีสิทธิ์โปรเจกต์ talevo ใน team etcstream และแก้ deployment limit ในบัญชีตามที่ Vercel ระบุ.
   เก็บ release ไว้สำหรับ deploy ด้วยสิทธิ์บัญชีเดิมเมื่อพร้อม.
3. ใน Supabase Auth ตรวจ Site URL/Redirect URLs ให้คง pages.dev, workers.dev และ Vercel ที่ใช้อยู่;
   เปิด Google provider เฉพาะเมื่อมี OAuth client/secret ของเจ้าของ และทดสอบ PKCE callback ด้วยบัญชีทดสอบ.
4. ลงทะเบียน MFA สำหรับบัญชีผู้ดูแล และเตรียม flow challenge/step-up ก่อนบังคับ aal2 ใน RLS/RPC;
   ไม่มีการเปิด MFA ที่ทำให้ผู้ดูแลล็อกตัวเองออกจากระบบในครั้งนี้.
5. ตรวจ Auth rate limits, leaked-password protection และ CAPTCHA ตามแพ็กเกจ Supabase;
   edge ของ TALEVO ไม่สามารถจำกัดการยิงตรงไป Supabase Auth ได้.
6. ตรวจ backup ล่าสุดใน Supabase Dashboard และทดสอบ restore ลง project ทดสอบก่อน release ที่เปลี่ยนฐานข้อมูล.
   รอบนี้ไม่มี database backup/restore test จริง และไม่มีการเปลี่ยนข้อมูล production.
7. ถ้าต้องการรูปโปรไฟล์เป็นส่วนตัว ให้ review แผน private bucket + signed URLs ก่อนเปลี่ยน public flag.
8. ตั้ง Actions secrets ที่เอกสาร cloudflare-deployment.md ระบุหากจะใช้ auto-deploy;
   ตรวจ workflow run จริงก่อนถือว่า pipeline พร้อม. ไม่มี push ในงานนี้.

## Rollback และ incident response

Worker version ก่อนงานนี้: `ab64ad29-9d22-4497-96fe-28a2fd773f7b`.
Cloudflare Dashboard > Workers & Pages > talevo > Deployments เลือก version นี้และ Roll back.
Pages จะใช้ Worker version ที่ rollback ทันที เพราะ service binding คงเดิม.
การ rollback ย้อน security controls บางส่วนด้วย ควรใช้เฉพาะเมื่อมี regression ที่ยืนยันแล้ว.
ไม่มี SQL ใหม่ถูกรันในครั้งนี้ จึงไม่มีข้อมูลฐานข้อมูลที่ต้องย้อนกลับ.

โค้ด security แบ่ง commit `8ad87b3` และ `f35422f`;
ก่อน revert ให้เก็บงานค้างและตรวจ diff ของงานอื่น หลีกเลี่ยง reset --hard/git clean.
ในสำเนาแยกที่สะอาด ใช้ git revert f35422f และ git revert 8ad87b3 ตามลำดับ.
คำสั่ง rollback/deploy บน Vercel ต้องแก้สิทธิ์ก่อน.

หากพบ intrusion: เก็บ requestId/เวลา/route/status แบบไม่เก็บ token/password/body,
ตรวจ Cloudflare logs และ Supabase Auth logs, จำกัดบัญชี/traffic ที่ยืนยันผิดปกติ,
เพิกถอน session ผ่านผู้ดูแล และหมุนเฉพาะ key ที่ยืนยันรั่วเมื่อเจ้าของอนุมัติ.
ทดสอบการกู้คืนใน project แยกก่อนนำข้อมูลกลับ production.
